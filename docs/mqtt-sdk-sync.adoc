== MsQuic 使用方式的实际变化

旧 SDK 由两个 MQTT 协议实现直接调用 quic_api.c，open 时接收 URL/config，
以自有 socket/stream 对象管理连接；新实现采用以下路径：

[source,text]
----
MQTT 3.1.1 / 5 unified protocol
    -> nni_pipe
    -> mqtt/transport/quic
    -> nng_stream / nng_stream_dialer
    -> supplemental/quic/msquic_dial.c
    -> MsQuic
----

多流模式使用一条控制主流、两条 SUBSCRIBE 子流和两条 PUBLISH 子流。
每条流独立分帧并在原流回复 QoS ACK。
单流模式把所有 MQTT 流量送到主流，配置不再是无效的占位选项。
不再采用旧 SDK 的按 topic 建立流的实现。

MsQuic API/registration 按 dialer 管理，configuration 按连接管理；
一个连接关闭或修改配置不会覆盖另一个连接的全局配置。
发送采用独立缓冲区，取消用户 AIO 后仍保留 MsQuic 所需字节直到 SEND_COMPLETE。
连接释放通过 reaper 完成，避免在 MsQuic 回调线程等待自身退出。
接收遍历全部 QUIC_BUFFER，FIN 携带的数据正常交付；
通过 TotalBufferLength 报告同步消费量，让 MsQuic 保留尚未被接收 AIO 消费的数据。

TLS 使用 MsQuic 原生验证及 CA 文件接口，不移植上游手工 OpenSSL 验证器中的
X509_STORE_CTX 释放后访问；支持仅 CA 的服务端验证及带密码的客户端私钥类型。
TLS、超时、优先级和多流选项应在 dialer start 前设置。

== 附带修复

* CONNECT 和后续写入按实际 IOV 进度续写，避免从固定头小缓冲区读取 CONNECT 剩余内容。
* 处理逐字节 CONNACK 固定头/消息体，续读不会覆盖已有字节。
* 校验剩余长度和 Maximum Packet Size；拒绝 CONNACK 返回 NNG_ECONNREFUSED，
  reason code 可通过 dialer getter 读取。
* 保留 Maximum QoS=0，不在 pipe 初始化时重置协商结果。
  QUIC 对超过协商 QoS 的 PUBLISH 返回错误，不仅修改固定头而遗留非法 packet-id。
* Keep Alive 使用 CONNECT/Server Keep Alive，支持零值禁用 MQTT PING。
* 离线发送、在线 ACK 等待、接收 AIO 支持超时/取消；关闭清理未确认表后移除表项，
  避免 pipe/socket 二次清理同一消息。
* MQTT callback 与接收 AIO 同时使用时持有独立消息引用；QoS2 在 PUBREL 后交付。
* 底层发送立即失败会完成 AIO；取消后迟到的 SEND_COMPLETE 不访问已释放的 AIO。
* 会话票据在长度缩窄和 memcpy 前检查边界。
* 修正 PUBLISH 的 16 位 topic 长度、packet-id 边界及剩余长度解码越界。
* 同步 nng_sendmsg 无法返回 MQTT ACK 消息，成功时释放该消息；
  异步发送仍通过 AIO 返回 ACK。
* 修复断连回调条件、reason-code getter、配置字符串替换泄漏、
  ACK 队列状态和 QUIC 资源部分初始化的释放路径。

== 不迁入的服务端代码

不引入 conf_bridge_node、conn_param、bridge 队列和 AIO input 约定、
broker 状态机、合成连接/断连事件、MQTT Stream、exchange、raw_stream，
以及通过修改 MQTT 3.1.1 protocol version 高位实现的 no-local 扩展。
不增加 QUIC listener 服务端；SDK 客户端使用 stream dialer。
协议的 MQTT CONNACK 是实际服务端回包，不是 broker 专用通知对象。

== 应用接口迁移

新接口采用独立 dialer；包含 mqtt_quic_client.h 使用单参数 open。
旧 mqtt_quic.h 恢复 conf_quic、open(socket, url)、open_conf 和 ACK callback 的源码兼容入口，
旧方式在应用发送 CONNECT 时启动内部 dialer，后续自动重连沿用该 CONNECT。
调用方需要重新编译，不能把旧二进制直接链接到新 open ABI。
旧 ACK callback 参数仍为 AIO，消息由 callback 释放；成功后可用同一 AIO 调用
nng_recv_aio 排空 ACK 队列，空队列以 NNG_ECANCELED 结束。
新代码推荐使用发送 AIO 读取 ACK。conf_quic_tls_free 只释放 helper 创建的配置。
两个 QUIC 示例已按新方式更新并编译通过。

[source,c]
----
nng_socket sock;
nng_dialer dialer;
nng_msg *connect;

/* MQTT 5 使用 nng_mqttv5_quic_client_open。 */
nng_mqtt_quic_client_open(&sock);
nng_dialer_create(&dialer, sock, "mqtt-quic://127.0.0.1:14567");
nng_dialer_set_bool(dialer, NNG_OPT_QUIC_ENABLE_MULTISTREAM, true);

nng_mqtt_msg_alloc(&connect, 0);
nng_mqtt_msg_set_packet_type(connect, NNG_MQTT_CONNECT);
nng_mqtt_msg_set_connect_proto_version(connect, 4);
nng_mqtt_msg_set_connect_keep_alive(connect, 60);
nng_mqtt_msg_set_connect_clean_session(connect, true);

/* 设置成功后 CONNECT 由 dialer 持有；不要再 send/free 此消息。 */
nng_dialer_set_ptr(dialer, NNG_OPT_MQTT_CONNMSG, connect);
nng_dialer_start(dialer, 0);
----

上例省略返回值检查；实际示例包含连接错误处理。
独立 dialer 接口的 CONNECT 必须在 start 前设置；旧兼容入口仍通过 send CONNECT 启动。
连接/接收 callback 的消息仅在 callback 内借用，需要保留时使用 nng_msg_dup；
接收 AIO 返回的消息由应用释放。
ACK 使用发送 AIO 的结果消息读取；同步 nng_sendmsg 只返回完成状态。

=== 构建失败及修复

之前的 TLS=ON 构建不足以覆盖 QUIC=ON 的默认配置。
在新建的 build-sdk-sync/default-only 中仅传入 -DNNG_ENABLE_QUIC=ON，

此外修复 DEBUG=ON、ASAN/TSAN=OFF 时 nng_testing 丢失依赖链接的问题。

=== 本次实际复现并修复的问题

* 在线 QoS 发送超时后，调用方按 nng_sendmsg 错误返回约定释放原消息，会触发 ASan UAF。
  现在调用方、未确认表和传输分别持有引用；错误保留调用方原消息，ACK 成功才消费原消息。
* 多流 SUBSCRIBE 随机选流，UNSUBSCRIBE 却走控制流；公网返回 UNSUBACK 后仍能收到消息。
  现在订阅变更统一使用同一数据流，支持多 topic 请求；PUBLISH 按 topic 稳定选流以保持顺序。
* context 关闭时，在线等待 ACK 或离线排队的发送没有结束，只能等待超时。
  现在显式 context 记录未完成发送并在关闭时取消；同一 context 同时只能有一个发送，
  普通 socket 的并发发送不受此限制。
* 重复设置 PUBLISH topic/payload 会遗失旧缓冲区；ASan 检出 64 个发送的旧 payload 泄漏。
  现在安全替换已有内容，处理输入别名；修改解码消息前复制借用的 topic 和 payload。
* 隔离旧 pipe 的关闭、定时器及发送回调，避免触碰新连接状态；连接状态 getter 加锁。
* MsQuic stream priority 使用拨号时的配置快照；重试间隔拒绝零/负值。
* SQLite 离线入队成功按成功转移所有权，入队失败保留消息；统计长度在刷盘释放消息前读取。

本地真实 MsQuic 集成程序包含 15 个场景，新增在线超时/取消所有权、context 在线/离线关闭、
64 个并发 QoS1 发送及同 topic 顺序、20 轮服务端关闭/畸形帧后的自动重连、无效重试间隔。
MQTT codec 回归另覆盖重复设置及修改解码后的 PUBLISH 缓冲区。
这些测试在 ASan/UBSan 下运行，未禁用 leak detection。
SQLite 分支虽参与 sanitizer 构建，本次未做数据库故障注入或长时间离线积压测试。

=== 已修复的关闭错误

带符号的 Release 堆栈确认，socket transport 的 panic 并非 endpoint mutex 失效，
而是 sfd_tran_pipe_stop 调用 nni_aio_stop 时，AIO 所属 expire queue 的 mutex 已销毁。
未完成协商的 pipe 仍由回调持有，但 endpoint fini 退出了 reaper 队列；
nni_reap_drain 因而可能提前返回，迟到的回调随后才排入 pipe 回收。

修复措施：endpoint 在 pipe 引用归零前一直留在回收队列，避免提前结束全局清理，
并移除 pipe fini 对同一 endpoint 的重复排队路径。未改 nanomq/nng。
新增 100 次 socket 关闭、nng_fini、重新打开回归；它还暴露了 reaper 的退出标志
跨初始化未清零的问题，现已修复。Release 的整个 socket 测试程序连续 20 轮通过，
包含 2000 次上述循环；相关 ASan/UBSan 测试通过。

MsQuic 后端也补上关闭等待：应用释放 stream 或取消拨号后，连接立即进入回收等待；
直到迟到的 SHUTDOWN_COMPLETE 释放最后引用才销毁 connection、configuration 及 dialer。
最终引用归零与回收检查使用连接锁同步，防止重复排队及释放后访问。
确定性测试延迟 shutdown 回调，验证 reap_drain 在回调到达前不能返回，资源恰好释放一次。
另增加真实 QUIC/TLS peer 尚存活时，关闭 SDK、nng_fini、重新打开十次的测试，ASan/UBSan 通过。

== 自审修复：PUBREC 原因码与流创建失败

复查新增 MQTT over QUIC 实现时发现并修复以下问题，新增用例均在修复前失败：

* MQTT 5 收到失败 PUBREC（原因码不小于 `0x80`）后仍发送 PUBREL。
  现在将该 PUBREC 作为终止 ACK，移除对应未确认 PUBLISH，并通过发送 AIO
  返回原始 PUBREC。AIO 的成功表示获得协议响应，调用者仍需检查 ACK 内容，
  与现有 PUBACK/PUBCOMP 约定一致。
* 自动回复 PUBREL/PUBCOMP 等 ACK 时错误复制对端的原因码与诊断属性。
  例如 PUBREC `0x10` 被复制成非法 PUBREL 原因码。现在自动回复使用自身成功状态，
  不回传对端属性。本地 MsQuic 集成用例覆盖拒绝原因 `0x87` 及成功原因 `0x10`。
* `StreamOpen` 成功但 `StreamStart` 同步失败时遗漏 `StreamClose`。
  同步失败没有排队启动操作，不会产生负责清理的流回调。现在立即关闭并清空句柄，
  保留异步启动失败由回调清理的逻辑。模拟 API 单元用例验证关闭恰好发生一次。

最终验证：用户完整参数的 Ninja 静态 MsQuic + Debug + ASAN 完整编译通过，

== nng_stream / MsQuic 接口契约专项复查

直接检查 stream dialer 的 dial/close/free、stream 的 send/recv/cancel/close/free、
AIO 队列与 MsQuic callback 的交接，不通过 MQTT 封装掩盖底层错误。
本轮修复：

* 此前 NanoSDK 的 `currcon` 持有已交付 stream 的连接，导致排队第二次拨号
  返回 EBUSY，且释放 dialer 会关闭调用者已经持有的 stream。
  现在 `currcon` 只表示尚未交付的拨号；成功交付前即清除。
  已交付 stream 通过自己的引用保留底层 dialer/registration/API 生命周期。
* 上游和此前 SDK 的 `quic_dialer_free` 都先停止内部 AIO，未先完成排队用户 AIO。
  现在先执行 close，完成所有用户 AIO，再停止内部 AIO 和销毁拨号器。
  同时兼容只完成部分初始化的错误清理路径。
* 使用显式 `dialing` 状态标识未处理完毕的底层拨号结果，避免把内部 AIO
  的 callback busy 状态误作拨号状态。取消最后一个请求后，将旧拨号标记为丢弃，
  防止立即新排队的请求继承旧的 ECANCELED 或旧连接。
* 原生拨号取消和连接 shutdown 都在完成 AIO 之前清除对应 `currcon`；
  避免 AIO 回调立即重拨时看到旧连接返回 EBUSY。
* 对端已发起关闭、但尚未发出 SHUTDOWN_COMPLETE 时，本地 stream close
  仍立即完成挂起的读写 AIO，不因 closed 标志提前返回而留下等待。
* 子流异步 START_COMPLETE 失败后，通过 shutdown 清理句柄，再五秒退避重试；
  避免在失败 callback 间无间隔创建流。用独立 retry_pending 状态替代
  `nni_aio_busy`，避免重试 callback 尾部和新 stream-start 失败交错时漏掉重试。
* 发送 iov 跳过零长度段的 memcpy，允许零长度段使用 NULL 地址。

新增真实 MsQuic 用例覆盖：同一拨号器并行排队两个拨号、释放拨号器后两条
stream 独立收发、释放时完成两个 pending 用户 AIO、连续二十次取消后立即重拨。
前两个所有权问题已先用新增用例复现（EBUSY / Object closed），再验证修复。
单元用例补充关闭窗口中的接收 AIO 完成、异步子流启动失败退避。

最终验证：完整静态 MsQuic + Debug/ASAN 构建通过，相关 CTest 10/10（69.89 秒）；
完整共享 MsQuic Release 构建通过，相关 CTest 10/10（71.90 秒）。

== 桥接调用链重审与发送路径重构（2026-11-03）

本节描述本轮实现，前面的测试数字属于此前版本。
对照入口是 NanoMQ `nanomq/bridge.c` 的 `nano_set_quic_config`、
`bridge_quic_client`、`bridge_quic_connect_cb`、`bridge_quic_disconnect_cb`，
以及其 nng 协议、传输和 MsQuic 适配实现。所有修改只发生在 NanoSDK。

实际调用链：

----
nng_dialer + CONNECT / QUIC 配置
  -> MsQuic connection / control stream START_COMPLETE
  -> nng_stream 交付给 MQTT QUIC transport
  -> CONNECT / CONNACK 协商成功后交付 nni_pipe
  -> pipe ADD_POST 回调发起订阅
  -> MQTT protocol 管理用户 AIO、Packet ID、QoS ACK / 超时
  -> nni_pipe_send / nni_pipe_recv
  -> MQTT QUIC transport 分流、帧解析、发送额度、同流回复
  -> nng_stream_send / nng_stream_recv
  -> MsQuic StreamSend / RECEIVE / SEND_COMPLETE
----

以前仅仅建立多条原生 stream，但协议与 transport 各自仍共用一个发送 AIO/
全局发送队列；这不等价于 NanoMQ qos_first 的并行路径。本轮重做如下：

* 协议层使用有上限的独立发送操作，每次操作独占 transport AIO。
  用户 QoS1/2、SUBSCRIBE、UNSUBSCRIBE 的 AIO 等待 MQTT ACK；原生
  SEND_COMPLETE 仅说明字节发送完成。用户、QoS 缓存、transport 分别持有
  消息引用，ACK 先到和用户取消不会提前释放 transport 正在使用的缓冲。
  所有协议发送均经 `nni_pipe_send`；协议层不直接调用 MsQuic。
* stream 路由只在 transport 决定。每条流独立 FIFO，保持同一主题顺序，
  一条流停滞不会阻挡其他流。自动 PUBLISH 路由到数据流 3/4，普通订阅及
  退订使用流 1；qos_first 的默认高优先级流恢复为 NanoMQ 使用的控制流。
  `nng_mqtt_quic_msg_set_stream(msg, 1..4)` 的显式选择优先。
* 移除忙时将 SUBSCRIBE 当作 QoS0 丢弃的路径，也不再对本地未发送的 QoS0
  静默丢弃并报告成功。发送容量不足返回错误；QoS0 成功在 transport 完成时
  通知，错误/取消保留调用者消息。旧 retry_qos_0 配置仍可接受。
* close 首先标记关闭并完成全部上层 send/recv AIO，再关闭原生 stream 和内部
  AIO。关闭后 recv 返回 ECLOSED；pipe stop 等待全部协议发送回调退出。
  endpoint 仍有协商中 pipe 时保留 reaper 可见性。
* MQTT 5 Receive Maximum 按 stream/Packet ID 记账：重复发送不重复扣额度，
  重复 ACK 不增加额度，额度不足排队等待；包大小检查失败不消耗额度。
* 接收队列满时实施背压。transport 每流最多额外保留一条完整消息并暂停
  读取；协议队列有空位后恢复读取，不再继续 ACK 后直接丢弃接收消息。
* MsQuic 的 SetParam 和 StreamClose 在非 worker 线程可能同步等待 worker。
  stream priority 改在 START_COMPLETE 回调设置；同步 StreamStart 失败清理时
  释放连接锁后执行 StreamClose，并防止旧句柄 shutdown 回调重复关闭。

未导入 broker 的 conf_bridge_node、conn_param、topic remapping、broker 状态机、
MQTT Stream 服务端语义。SDK 保留独立 MQTT 客户端接口及旧 QUIC 兼容入口。

本轮也发现了影响上述链路的基础问题：

* ASAN 在通用 pubsub 的重连定时器中报告已释放 socket 的访问。
  根因是旧 AIO stop/close/abort 在没有 cancel_fn 时直接撤销 task busy 引用，
  但 provider 可能仍处在 begin/schedule 或 finish/dispatch 的窗口中。
  同步 NanoMQ 的提前取消状态和 schedule 错误处理，并将 fini 也改为等待
  provider 的真正完成，避免同一竞态在析构时重现。新增三个确定性时序用例。
* nng_mqtt_client_alloc 将 sub_aio 接到了发布 send_aio 的回调。
  改回订阅回调后，按 bridge.c 方式从 pipe 回调订阅、断线后重新订阅可运行。
* SQLite 保留连续回放能力，transport 发送失败的离线消息重新入库。
  修正 MQTT5 版本判断、数据库显式关闭后释放 option 的重复释放，以及目录
  字符串释放遗漏。真实 MQTT5 离线缓存回放测试覆盖这些路径。
* 离线队列第一条消息因流配置不支持而失败时，继续处理后续消息，避免等待
  一个根本不会出现的字节发送回调。测试在拨号前同时排入失败与有效消息。
  同时恢复发送报文类型校验，拒绝无 MQTT 元数据及服务端专用报文并保留
  调用者消息所有权。

新增验证：

=== 合并后的实现审查与修复

* main 的 TCP/TLS QoS 缓存已改为 socket 的 Packet ID → AIO 映射，
  不能直接覆盖为旧版 pipe 的 Packet ID → message 映射。
  保留 main 的结构，移植 nanwang-dev 的取消和关闭生命周期处理；

  验证超时、pipe 关闭和 socket 关闭都能结束全部 AIO。
* CONNECT setter 统一所有权，覆盖替换和重复设置同一指针；
  修正 keepalive 的毫秒单位、保留服务端协商值。
* 修正断线原因 getter 把 copyin 当作 copyout 使用的问题；
  初始化非 PUBLISH 发送路径的 qos，避免 SQLite 分支读取未初始化值。
* 保留 main 的 MQTT 编解码校验及深复制更新，同时恢复 nanwang-dev

* 清除自动合并产生的重复 timestamp 字段、声明、QUIC 目录和 transport
  注册；QUIC 协议的 pipe_close 适配 main 的 int 返回接口；
  QUIC ACK 队列限制采用独立宏，避免与 main MQTT packet 宏冲突。
* 修复普通 OpenSSL 的服务器 CA/证书配置遗漏及未初始化返回值，
  保留国密客户端分派。保留普通 OpenSSL 和南网两种可构建配置。
* 移除重复 DEBUG/ASAN 配置；恢复 SCRAM 开关及依赖声明，

* main 的安装导出与 nanwang-dev 的 imported MsQuic 目标冲突：
  不再把 MsQuic 静态 INTERFACE 目标加入 nng 导出集合，避免重复定义

* 迁移 mqtt_full 回调及主题 API、multiurls_switch 的 CONNECT 模板复制；
  修复 MQTT5 QUIC 示例链接错目标、独立安装包链接及 SQLite 协议版本。

== 2026-11-09：Windows/macOS 兼容性静态修复

根据 Windows CI 的 zstd 配置失败和 macOS 的日志函数声明错误，审查同步代码的
平台依赖。按用户要求，本轮不下载或安装 Windows/macOS 工具链，不运行本机构建
或平台测试；只完成代码审查、修改和提交，原生编译结果交由后续线上 CI 确认。
以下内容是静态修复记录，不能视为 Windows/macOS 编译已经通过。

* 新增 `NNG_ENABLE_ZSTD`，默认 OFF。仅开启时查找 zstd、定义
  `NNG_SUPP_ZSTD`、编译压缩路径并向安装包消费者声明依赖。
  支持 zstd 包导出的 shared/static/generic target，默认 Windows/macOS
  及 Linux 构建均不再强制依赖 zstd。需要原压缩功能的构建应显式开启此选项。
* 未编入 zstd 时，Paho 的压缩连接/发送请求返回
  `MQTTASYNC_BAD_MQTT_OPTION`；不静默发送未压缩 payload。
  Paho 字符串复制改用 NNG 的可移植 helper。
* 日志进程标识统一走内部 helper：Windows 使用 `_getpid`，
  macOS/其他 POSIX 使用 `getpid`，Linux 保留 `SYS_gettid` 的线程标识。
  删除不存在的 `nni_plat_getpid` 调用，Linux syscall 头文件仅在 Linux 包含。
* Windows 屏蔽 POSIX syslog/Unix-domain datagram 日志代码，保留现有无操作入口。
  日志轮转的 size_t 格式使用 `%zu`，适配 Windows LLP64。
* 为 Windows 补充 `nni_timestamp`，使用已有的 `nni_time_get`
  转换 Unix epoch 毫秒，避免公共 timestamp API 在链接时缺少后端实现。
* 现有 SCRAM 实现含 POSIX 字符串函数及 MSVC 不支持的 C99 变长数组，
  因而 Windows 上将 `NNG_ENABLE_SCRAM` 约束为 OFF。
  未编入 SCRAM 时，TCP/TLS 启用请求返回 NNG_ENOTSUP，Paho 返回
  MQTTASYNC_BAD_MQTT_OPTION；不会声称已启用而实际跳过认证。
* 南网附带的库与 engine 为 Linux 专用，非 Linux 平台将
  `NNG_TLS_OPENSSL_HAVE_GM_NW` 约束为 OFF；普通 OpenSSL 不受影响。
* 共享 MsQuic 使用 `TARGET_LINKER_FILE`，使 Windows 链接导入库而非 DLL。
  使用 Linux `clock_nanosleep` 的公网 QUIC 测速程序仅在 Linux 构建，
  SDK QUIC 功能和可移植单元测试的开关保持独立。
* 使用 CMake 的 `CMAKE_POSITION_INDEPENDENT_CODE`，不再向 MSVC
  直接传入 GCC 的 `-fPIC` 参数。

本轮执行了差异检查和宏/依赖静态核对；未报告任何新的原生构建或运行通过结果。
